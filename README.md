16G 显卡跑通 Inkling 2 Mini
一张 RTX 5070 Ti（16G），把 Thinking Machines Lab 的 26.4B 循环层模型跑起来了。这里是能复现的全部东西：踩过的坑、显存怎么算的、能直接抄的启动参数。

一句话结论
官方加载器认不全循环层，换构建就通了；剩下全是显存预算的问题。

这模型是什么
总参数 26.4B，每 token 只激活 3.4B。稀疏 MoE，128 个专家一次走 8 个。中间那 12 层在推理时重复跑三遍，所以等效激活约 5.4B，层应用算下来 48 次。
第一次看到"权重约 20G"的时候我以为 16G 卡没戏，后来发现有 Q3，13.6G，勉强塞得进去。就这么开始了。
卡最久的地方：官方加载器不认这套结构
这一段最值得看，因为它不是参数问题，是工具链问题，你自己怎么调都调不出来。
一开始用官方 llama.cpp，编译、下载、跑，一切正常，然后卡在加载。表现是加载到最后对不上，或者勉强进去了，一句话问下去它开始复读同一段话，翻来覆去。
我先怀疑量化坏了，重下了两遍权重。又怀疑显存不够，参数改了一轮。都不是。
真正的原因很朴素：官方加载器对循环层支持不全。中间 12 层要重复跑三次，普通加载路径按 24 层算，到那儿就错位了。
换了他家自己改的构建才通。我用的是构建号 b12631-mix-acc0843 的那个（仓库地址自己找，版本变太快，别抄我的）。
换完之后一次加载过。问它一句中文，反馈节奏明显是"先在心里过了一遍再答"——不是卡，是真的多跑了几遍。
显存这点账
13.6G 权重上卡之后，剩下的不是十三点六，是十六减十三点六，二点四。
然后这二点四不是你的：
Windows 桌面合成加浏览器硬件加速，正常吃 0.8 到 1.5 G。我挂着一个 Chrome 和一个 Electron 客户端，一开模型直接飙到 15.9
mmproj 那个视觉投影层，又一个 G 上下。纯文字对话先别加载
所以真正留给 KV cache 的大约 1.5 G。8K 上下文是稳的，往上试到 16K 看运气。标称的一百万 token 是给规格表看的，跟 16G 卡没关系。
能直接抄的参数
llama-server \
  -m inkling-2-mini-Q3_K_M.gguf \
  -ngl 99 \
  --n-cpu-moe 8 \
  -c 8192 \
  -fa \
  -ctk q8_0 -ctv q8_0 \
  -ub 256 \
  --host 127.0.0.1 --port 8080

Windows 用户改三个路径就能跑：见 start-llama.bat。
两个参数值得单独说：
--n-cpu-moe 把专家层甩到内存。128 个专家没必要全塞显存，注意力、路由、共享层留在卡上，专家交给 CPU。这一开显存能掉好几个 G，代价是速度打折。从 8 起步，稳了往上加。
-ctk q8_0 -ctv q8_0 把 KV 压到八位，差不多省一半。这个不开，上下文别想上去。
Q3 的坑：误差会被循环放大
中间 12 层跑三遍，量化误差跟着放大三遍。
表现是偶尔"想歪"：同一个意思换个说法说三遍，或者刚说完一句又自己否定掉。不是参数调错，是量化太狠。
Q3 当"能跑通"的配置，正式用还是 Q4。等 --n-cpu-moe 调顺、显存有余量，Q4_K_M 塞得进去，质量差别听得出来。
起来之后怎么用
llama-server 给的是 OpenAI 兼容接口，指向 127.0.0.1:8080，任何能改 base_url 的客户端直连，不用额外适配。
curl http://127.0.0.1:8080/v1/chat/completions \
  -H "Content-Type: application/json" \
  -d '{"messages":[{"role":"user","content":"用一句话解释循环 Transformer"}]}'

几句实话
这模型通识一般。问它现在什么政策、哪个牌子多少钱，它会一本正经给你编，编得还挺顺。让它处理你手上的材料没问题，让它告诉你世界长什么样，不行。
别和绘图模型一起跑。13.6G 加 Flux 必炸，要换着用就写个脚本，先卸这个再起那个。
还有，它出生才三天，生态还在磨。遇到奇怪报错先怀疑适配层，别怀疑模型本身——我昨晚那三个小时就是这么浪费掉的。
