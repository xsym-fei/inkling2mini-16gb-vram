# 16G 显卡跑通 Inkling 2 Mini，以及我跑了三天才发现它一直在 CPU 上

一张 RTX 5070 Ti，16G 显存。Thinking Machines Lab 在 11 月 20 号放了 Inkling 2 Mini 的权重，26.4B 总参数、循环层结构、Apache 2.0，我当天就下了。

中间卡了三天。不是因为模型难跑，是因为**它一直在 CPU 上跑，而我不知道**。

这篇文章把两件事写清楚：怎么让它真的上卡，以及中间几个会静默失败、不报错的坑。

## 先说结论

- 官方 llama.cpp 加载器认不全循环层，必须用改过的构建
- 光有 `ggml-cuda.dll` 没用，还得装 CUDA 13 运行库，缺了它 `-ngl 99` 是完全白写的
- 缺运行时的时候它不报错，只是安静地跑在 CPU 上，15 倍慢
- 补上之后：12.4 tok/s → 53 tok/s

## 这模型是什么

总参数 26.4B，每 token 只激活 3.4B。稀疏 MoE，128 个专家一次走 8 个。中间那 12 层在推理时重复跑三遍，等效激活 5.4B，层应用算下来 48 次。

Q3 量化后 12.7 GB，加视觉投影层 0.6 GB，16G 卡塞得下，但塞得很满。

## 第一个坑：官方加载器不认循环层

用官方 llama.cpp 编译、下载、跑，一切正常，然后卡在加载。表现是加载到最后对不上，或者勉强进去了，一句话问下去它开始复读同一段话。

我先怀疑量化坏了，重下两遍权重。又怀疑显存不够，参数改了一轮。都不是。

原因是：中间 12 层要重复跑三次，普通加载路径按 24 层算，到那儿就错位了。换成他家自己改的构建才通（我用的是 `b12631` 这个构建号，具体仓库自己找，版本变得快）。

## 第二个坑，也是最贵的那个：它其实没上卡

换完构建，能对话了，12.4 tok/s。我以为这就是 16G 卡跑 26B 模型的正常水平，还挺满意。

直到我随手看了一眼 nvidia-smi。

```
显存占用：1769 MiB（推理全程不动）
GPU 利用率：6%
功耗：37 W
llama-server 内存：12.76 GB
```

**权重 12.76G 全在系统内存里，显卡基本在睡觉。** 12.4 tok/s 是纯 CPU 的成绩，我拿它当 GPU 成绩夸了两天。

为什么会这样？这个构建确实带了 CUDA 后端，`ggml-cuda.dll` 有 401MB，但它依赖 CUDA 13 的三个运行库：

- `cudart64_13.dll`
- `cublas64_13.dll`
- `cublasLt64_13.dll`

机器上一个都没有——没装 CUDA Toolkit，System32 里也没有。CUDA 后端初始化失败之后，**它不报错，直接静默回落到 CPU**，`-ngl 99` 这个参数就这么白写了。

一句命令就能验证：

```bash
llama-server.exe --list-devices
```

装之前输出 `Available devices: (none)`，装之后才是 `CUDA0: NVIDIA GeForce RTX 5070 Ti`。

### 怎么补

从 NVIDIA 官方分发包取（不用装整个 Toolkit）：

```
https://developer.download.nvidia.com/compute/cuda/redist/
cuda_cudart/windows-x86_64/cuda_cudart-windows-x86_64-13.1.80-archive.zip      2.9 MB
libcublas/windows-x86_64/libcublas-windows-x86_64-13.2.0.9-archive.zip       384 MB
```

解压后把三个 dll 从 `bin\x64\` 里捞出来，直接扔进 `llama-server.exe` 所在的目录。不用配环境变量，不用装驱动，重启服务就认。

补完第一件事就是跑 `--list-devices`，看到 `CUDA0` 才算真上卡。加载时间从 60 秒级降到 14 秒，也能当旁证。

## 第三个坑：`-fa` 在这个构建里必须带值

想开 flash attention，顺手写了 `-fa`，结果启动直接退出：

```
error: unknown value for --flash-attn: '--no-warmup'
```

这个构建的 `-fa` 要求显式给 `on/off/auto`，不给值的话它会把后面那个参数当成值吃掉。写成 `-fa on` 就正常。

这个错误至少会报出来。前面那个 CUDA 静默回落才是真要命的。

## 实测数据

同一台机器，同一份权重，只改运行条件：

| 配置 | 上下文 | 生成速度 | 预填充速度 | 显存 |
| --- | --- | --- | --- | --- |
| 没装 CUDA 运行库（纯 CPU） | 8192 | 12.4 tok/s | 18–24 tok/s | 1.77 GB（显卡没参与） |
| GPU，默认参数 | 8192 | 48.7 tok/s | 70.1 tok/s | 15.6 GB |
| GPU，`-fa on` + KV q8 | 8192 | 55.5 tok/s | 69.8 tok/s | 15.1 GB |
| 同上 | 16384 | 52–53 tok/s | 59–61 tok/s | 15.2–15.7 GB |
| 同上 | 32768 | — | — | 15.7 GB |
| 同上 | 65536 | — | — | 15.8 GB |

生成速度 4 倍多，预填充 3 倍。装运行库这半小时，是整个流程里性价比最高的一步。

（预填充速度在 16K 那档反而略低，是因为上下文开大了注意力计算变重，不是配置问题。）

## 上下文能开多大

8K、16K、32K、64K 我都试了，全都能起来。显存几乎不随上下文增长——24K 比 16K 只多 10MB，64K 才到 15.8 GB。

但别被这个骗了。64K 那档只剩不到 450MB 余量，开个浏览器、挂个微信，就可能 OOM 崩掉。

**我最后定在 8K**：显存 15.1 GB，留 1.2G 给桌面和浏览器，日常对话完全够。而且 8K 反而比 16K 快一点——55.5 对 53，上下文开大了注意力计算更重，跑得更慢。

这一条挺反直觉的：**不是上下文越大越好**。除非你要塞长文档，否则 8K 是最划算的那档。

于是一百万 token 的标称上下文，在 16G 卡上实际能稳用的就是两位数 K。规格表是规格表，显存是显存。

## 显存这点账

12.7G 权重 + 0.6G 视觉层 = 13.3G，剩下的才是你的。

- Windows 桌面合成 + 浏览器硬件加速：0.8–1.5 G。开着 Chrome 和 Electron 客户端，光这一项就能把 16G 吃穿
- KV cache（q8 量化后）：开 8K 到 64K 之间差别不大，几十 MB 级别
- 安全余量：至少留 0.5 G，低于这个就开始抖

## 能直接用的一套参数

```bat
llama-server.exe -m "D:\DSH 对话\AI\gguf\q3.gguf" --mmproj "D:\DSH 对话\AI\gguf\mmproj.gguf" ^
  -ngl 99 -c 8192 -fa on -ctk q8_0 -ctv q8_0 -ub 256 --no-warmup --port 8080 -t 8
```

三个参数值得单独说：

- `-ngl 99` 能上卡的全上卡。但**先确认 `--list-devices` 有 CUDA0**，否则这行等于没写
- `-fa on` 开 flash attention，必须带值
- `-ctk q8_0 -ctv q8_0` 把 KV 压到八位，省一半，这是上下文能往上开、同时留出显存余量的原因

Windows 上一键启动脚本见 `start-llama.bat`，改三个路径就能跑。

## Q3 的坑：误差会被循环放大

它中间 12 层跑三遍，量化误差跟着放大三遍。

表现是偶尔"想歪"：同一个意思换个说法说三遍，或者刚说完一句又自己否定掉。不是参数调错，是量化太狠。

Q3 当"能跑通"的配置，正式用还是 Q4。16G 卡上 Q4 加上 KV 量化，上下文大概要压到 8K 才有余量，这是个取舍。

## 几句实话

这模型通识一般。问它现在什么政策、哪个牌子多少钱，它会一本正经给你编。**让它处理你手上的材料没问题，让它告诉你世界长什么样，不行。**

别和绘图模型一起跑。13.3G 加 Flux 必炸，要换着用就写个脚本，先卸这个再起那个。

还有，它出生才四天，生态在磨。遇到奇怪报错，先怀疑适配层——不过更要小心的是**那些不报错的情况**，比如我这三天。
